## 3. Получение данных VK

Уже выбран и проверен официальный VK API. HTML-страница списка альбомов раньше перенаправляла на вход или проверку; VPN и регион могли влиять на доступ. Браузерная сессия и отдельный VK-аккаунт обсуждались как запасные варианты, но сейчас не нужны: API успешно заработал с сервисным ключом приложения, сохранённым локально.

Пользователь получил отчёт: official_vk_api, api_read_verified=true, token_saved=true, albums_received=100, album_title=1199, photo_count=12, order_matches_reference=true, discord_modified=false. Число 100 — размер полученного результата проверки, не доказательство отсутствия других альбомов.

Ключевые правила:
- Номер главы берём из названия альбома.
- Порядок фотографий берём из VK и сохраняем. Сообщество публикует альбомы для чтения, пользователь подтвердил правильность порядка. OCR, угадывание номеров страниц и дополнительная ручная проверка порядка не нужны.
- У одного номера главы могут быть РАЗНЫЕ альбомы: пустой и отдельный заполненный. Это не обязательно заполнение того же album_id. Нельзя навсегда помечать главу обработанной по первому пустому альбому.
- При нескольких непустых подходящих альбомах не выбирать случайный молча; сохранить понятную диагностику существующего поведения.
- Сохранять существующие проверки целостности скачивания, обработку ошибок API и порядок страниц.

## 4. Автоматический цикл и готовность главы

Согласованная схема:
1. Программа стартует при входе пользователя в Windows через Планировщик.
2. Определяет последнюю ПОЛНОСТЬЮ опубликованную главу бота по основному Discord-каналу и её ветке.
3. Обычно ожидаемый номер = последняя полная глава + 1.
4. Поиск новых глав — с 12:00 до 24:00 по Москве, раз в 30 минут.
5. После обнаружения непустого альбома начинается наблюдение за стабильностью.
6. После готовности скачивается глава и публикуется в Discord.

Это фоновый обработчик с внутренним ожиданием, а не обязательно повторный запуск приложения Планировщиком каждые 30 минут. Разбиение ожидания на короткие отрезки нужно для реакции на управление. Точные детали текущей v9 проверь по исходникам.

Текущая длительность наблюдения — 10 минут: успешные снимки примерно в моменты 0, 5 и 10 минут. Первый снимок считается началом наблюдения. Проверяется стабильность состава и порядка страниц; при изменениях наблюдение начинается заново. Не возвращай старые 15 минут из v7. Перерывы и ошибки нельзя засчитывать как подтверждённую стабильность.

После успешной АВТОМАТИЧЕСКОЙ публикации действует пауза на поиск и автоматическую публикацию на 72 часа. Публикация после РУЧНОЙ проверки эту паузу не устанавливает. Ручная проверка должна оставаться доступной при ручной паузе автоматики и обходить ограничения обычного автоматического поиска. Сверь реализацию с этими требованиями.

Позднее согласована отдельная доработка наблюдения, пока НЕ реализованная:
- Если при обнаружении альбома последняя известная активность старше 10 минут, наблюдать 5 минут.
- Для свежего альбома или неизвестного времени — 10 минут.
- Ориентироваться на обновление альбома и время самой новой фотографии, а не только создание альбома; существующее обсуждение предполагает выбор наиболее позднего достоверного времени.
- Изменение состава во время наблюдения возвращает полное наблюдение.
- Время — вспомогательный признак, а не гарантия полноты главы.
Не включай эту доработку незаметно в текущую задачу с кнопками.

## 5. Что считается опубликованным и где состояние

Пользователь ЯВНО отверг прежнее предложение держать неоткатываемый локальный счётчик успешных глав. Основной ориентир — фактические полные публикации в Discord.

Доступный код проверяет карточку бота и полноту её ветки. Удаление последней главы может сделать её следующей для повторной публикации, если в канале остаётся предыдущая полная глава. При пустом канале действует отдельная начальная точка, чтобы не выгрузить весь архив автоматически.

Локальное состояние всё равно нужно для скачивания, наблюдения, незавершённых отправок, защиты от повторов и восстановления после сбоев. В известном коде оно разнесено по state/<guild_id>/<channel_id>/; наблюдение источника хранится в watch_-334424.json. Поле expected — производное состояние: обычная ручная правка этого числа может быть перезаписана расчётом по Discord.

Для удалённой последней главы существующий Pipeline.publish предусматривает сохранение прежней завершённой квитанции в историю, чтобы старый complete=true не блокировал допустимую повторную публикацию. Сверь это с текущей v9, а не только v7.

Незавершённые публикации восстанавливаются: потеря ответа после POST не должна вызывать слепую повторную отправку. После фактической загрузки всех страниц, но потери финального редактирования, нужно сначала подтвердить финальную карточку и только затем отмечать завершение локально. Завершённые старые публикации массово не переписывать. Отдельные утилиты для изменения старых сообщений пользователю не нужны.

## 6. Discord: оформление и поведение

Текущий сервер — Exp., канал #giveaways. Это ТЕСТОВЫЙ канал, пользователь специально поправлял помощника: выбор канала не означает разрешение считать программу production-ready.

Известные идентификаторы текущей настройки:
- guild_id: 559346592377995266
- channel_id: 682105593699500038

Они даны для сверки, не должны подменять будущие настройки. Бот теперь называется OneDelivery; раньше в скриншотах был Sapphire. Не делать вывод о смене токена только из смены имени.

Главная карточка отправляется в основной канал. От неё создаётся отдельная публичная ветка главы, туда отправляются страницы. Обсуждения пользователей идут в ветке. Предполагаемый режим основного канала: бот пишет объявления, пользователи реагируют; обсуждают в ветках. Не меняй права сервера без указания пользователя.

Вид карточки ВО ВРЕМЯ загрузки:

    **ГЛАВА 1200**
    Страниц: 16
    Глава загружается в: <#THREAD_ID>

ПОСЛЕ подтверждённой отправки всех страниц редактируется ТА ЖЕ карточка:

    **ГЛАВА 1200**
    Страниц: 16
    Опубликовано в: <#THREAD_ID>

Нужно именно нативное упоминание ветки <#ID>, отображающееся компактной плашкой. Пользователь несколько раз просил убрать длинный URL discord.com/channels/....

Ветка создаётся от уже отправленной карточки, поэтому непосредственно до её создания карточка кратко может содержать только номер и число страниц. После создания ветки строка загрузки добавляется ДО отправки страниц.

Сообщения внутри ветки:

    Страницы 1-6
    [изображения под спойлерами]

Следующая группа — аналогично. Без общего числа через слеш, технических маркеров, хешей, версий и ссылок VK. Номер главы автоматически из названия альбома. Прежние служебные подписи со скриншотов — устаревшее оформление.

Действующее группирование — до 6 картинок в сообщении с учётом размеров файлов. В известном коде лимит группы также 24 MiB, а Discord API имеет отдельное ограничение числа вложений. Не расширяй группы и не меняй ограничения без проверки актуальных правил и необходимости. Спойлеры делаются через имена вложений SPOILER_0001.jpg и т. п. Не изменять исходники изображений без обоснования.

Уведомления:
- Корневая карточка — обычная отправка, без SUPPRESS_NOTIFICATIONS.
- Страницы — тихая отправка, чтобы не создавать несколько уведомлений на главу.
- Финальное редактирование не создаёт второго объявления.
- В известной реализации flags: 4 для карточки, 4096 | 4 для сообщений с вложениями; allowed_mentions.parse остаётся пустым. Персональные настройки Discord тоже влияют на уведомления.

Пользователь подтвердил после последнего обновления: повторно загрузил 1200, всё работает и оформление правильное. Этот тест завершён; не предлагай снова искать отсутствующую 1201 как проверку оформления и не перепубликуй ничего самовольно.

## 8. Последнее обновление и ошибки установщика

vk_card_update_v2/ содержит проверенное узкое обновление оформления: publisher_patch.py, worker_shutdown.py, apply_card_update.ps1, APPLY_CARD_UPDATE.cmd, README.txt, TESTING.md и тесты.

publisher_patch.py проверяет структуру фактических исходников v9 через AST, подготавливает изменённые файлы и резервные копии, сверяет хеши и заменяет файлы через os.replace. При неподдерживаемой структуре отменяет установку. Это не полная замена v9 снимком v7. Обновляются publish_album_v3.py и ongoing.py. Маркер идемпотентности — # VK_CARD_STATUS_UPDATE_1.

Исправленные проблемы:
- Ранее .NET File.Replace(..., null) падал с ошибкой формы пути. Используется Python/os.replace.
- Первый установщик карточки сразу после Stop-ScheduledTask пробовал блокировку и выдавал необоснованное «запущено вручную». Статус Планировщика не заменяет проверку реальной блокировки.
- В v2 ожидание фактического освобождения блокировок до 30 секунд.
- Во время применения обновления блокировки захватываются снова и удерживаются до конца замены или отката.
- Занятость приводит к понятной отмене до замены файлов, без принудительного завершения процессов.
- Восстанавливается прежнее состояние задачи: Enabled/Disabled и Running/Ready; затем открывается окно состояния.
- Ошибка сохранения необязательного отчёта не должна откатывать уже успешно установленный код.

Защита — именованная Windows-блокировка канала и файловая publisher.lock. Не снимай её ради удобства. Секреты, история, расписание и пользовательские настройки при обновлении сохраняются.

Пользователь выполнил v2 и прислал успешный результат: prepare completed, Publisher locks released, apply completed, Card update installed. Создана резервная копия в updates/card_status_v2_20261128_000213_903 внутри установленной папки. Затем подтверждена успешная публикация 1200.

## 10. Сейчас согласованы следующие доработки

А. Простая СМЕНА единственного Discord-сервера и канала из интерфейса.
Я отверг предложение усложнять приложение несколькими направлениями рассылки. Нужно изменить существующее место публикации. Проверять доступ бота; не запускать публикацию или перенос старых сообщений только ради проверки настроек. Смена назначения должна сохранять целостность состояния и защиту от параллельного запуска. Учти, что имя задачи Планировщика и состояние связаны с guild/channel: одной правки подписи в окне недостаточно.

Б. Кнопка ручного изменения ожидаемой главы.
Нужно, чтобы введённое число действительно управляло следующим поиском и не перезаписывалось немедленно обычным latest+1. Не отключать незаметно защиту от повторной отправки полной существующей главы.

Предыдущий помощник ПРЕДЛОЖИЛ семантику: ручной номер действует до успешной публикации, затем возврат к автоматическому расчёту; нужна также кнопка «Вернуть автоматический выбор». Наличие самой возможности я запросил явно; подробная семантика предложена помощником и ещё не проверена в реализации. Обозначь выбранное решение до внесения существенных изменений и не выдавай предложение за готовую функцию.

Для нового пустого канала продумать явную начальную точку, чтобы не отправить весь архив. Пользователь хочет простое управление, без ручного редактирования JSON и лишних подтверждений на каждом шаге.

## 11. План подготовки к продакшну и взаимодействие

Ранее был план из 7 этапов. Пользователь требует выполнять их по очереди и отдельно согласовывать каждый. Первые два этапа охватывали окно/трей и управление с заменой иконки; они выполнены. Исходный полный текст всех семи пунктов в доступном контексте не восстановлен: не выдумывай его и не называй новую идею «третьим этапом» без объяснения.

Если меняешь план, прямо назови изменение и причины. Держи меня в курсе архитектурных решений. Не объявляй тестовую установку продакшном. Не делай незапрошенный большой рефакторинг, миграцию на SQLite, упаковку в EXE или мультисерверную архитектуру под видом текущих кнопок.

Работай самостоятельно в уже одобренном объёме; не проси повторно разрешения на каждое чтение, проверку или обратимую подготовку кода. Отдельные новые этапы, внешние публикации и существенное изменение поведения согласовывай предметно, после подготовки конкретного результата.

Мне не нужны лишние ручные проверки, неоднозначные сообщения консоли, технические идентификаторы в пользовательских сообщениях Discord и повторный ввод уже настроенных токенов. Объясняй просто, но точно. Ошибки называй честно: неизвестный владелец блокировки не означает «запущено вручную», подготовка обновления не означает его установку.

НЕ ДАВАЙ веб-ссылки на скачивание файлов: они открываются в браузере, хотя я работаю в настольном приложении. Это неоднократно оговорено. Передавай готовые файлы через локальную папку проекта и указывай их имена/расположение.

## 12. Git: фактическое состояние и препятствие

Я потребовал перейти на нормальную работу с Git вместо множества папок и архивов.

В корне рабочей папки выполнен git init -b main. Но первого коммита НЕТ, индекса при последней проверке тоже не было. Удалённый репозиторий не настроен. Никакого push на GitHub не было. GitHub как сервис не обязателен для локального Git; создание удалённого репозитория отдельно не согласовано.

Подготовлены .gitignore, .gitattributes, README.md, DEVELOPMENT.md и AGENTS.md. .gitignore использует список разрешённых папок и исключает секреты и runtime-данные, архивы и transfer-папки. Вложенный .gitignore v7 также исправлен, чтобы requirements.lock не выпадал из Git вместе с publisher.lock. Перед первой попыткой добавления проверены 67 файлов (~396 KB), явных токенов и приватных ключей не обнаружено; новый handoff добавит ещё один документ.

Предыдущая среда работала как CodexSandboxOffline, владелец проекта — micpo. Git сообщал dubious ownership. Использовался только параметр конкретной команды -c safe.directory=<точный абсолютный путь проекта>; не применялся wildcard и не менялись глобальные настройки.

Git add упал: Permission denied при создании .git/index.lock. Запрос выполнения с дополнительными правами был отклонён ДО показа пользовательского подтверждения, потому что действующая granular policy запрещала sandbox_approval и request_permissions. Это ограничение той среды, а не доказанная неисправность Git или Windows.

В новой среде сначала проверь фактическую политику и возможность обычной записи Git. Не считай старое ограничение автоматически действующим и не считай переход в Codex гарантированным исправлением. При запрете используй только разрешённый механизм согласования; не обходи ограничения через другой GIT_DIR, индекс, изменение ACL, всеобщий safe.directory или отключение защиты.

Имя/email автора Git в прежней среде не были настроены. Предлагался технический автор Codex <codex@local.invalid> через параметры отдельной команды, но коммита с ним не было. Не выдумывай личные данные пользователя и не меняй глобальный Git config без необходимости.

Git хранит код и проверяемые изменения. Токены Discord/VK, DPAPI-файлы, config.json, state, downloads, logs, cookies, виртуальные среды и рабочие изображения в него не включаются. Существующие секреты остаются в пользовательской установке. Никогда не проси прислать их в чат и не печатай в вывод.

## 13. С чего начать прямо сейчас

1. Прочитай файлы проекта и этот handoff, проверь Git и разрешения новой среды. Коротко сообщи, что доступно и что блокирует работу.
2. Зафиксируй доступные исходники и документы первым коммитом, если среда разрешает. Подпиши исходную точку честно: полный актуальный v9 пока не получен.
3. Получи актуальный установленный код разрешённым способом, сверяй версии и сохрани импорт отдельно. Проверь состав зависимостей и вспомогательных ресурсов, чтобы новая установка была воспроизводимой.
4. Перейди к согласованным двум настройкам в отдельной ветке. Сохрани основной цикл работы. Перед существенными решениями объясни, как будут работать смена назначения и ручной номер.

Не начинай с повторного создания бота, настройки токенов, поиска отсутствующей главы или новой рассылки. Продолжай уже работающий проект с этой контрольной точки.
