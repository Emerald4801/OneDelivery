группы и окончательного подтверждения. Ошибка наблюдателя не прерывает отправку.
После перезапуска сохранённые группы читаются из незавершённой квитанции.
В форме назначения ошибка остаётся красной, введённые значения сохраняются,
кнопка предлагает повторить сохранение; успех обновляет основной экран.

## Единая обработка ошибок и восстановление

28.11.2026 пользователь согласовал следующий этап стабилизации. Реализация
подготовлена в codex/recovery-policy, контрольная метка — tested-recovery-2026-11-28.
Установка и реальные публикации остаются отложенными.

Независимый failure_policy.py классифицирует причину по типу исключения,
признаку retryable и HTTP-коду. Discord, VKSource/VK API и загрузчик сохраняют
эту классификацию при оборачивании ошибок. Сетевые ошибки и временные ответы
сервиса повторяются; ошибки прав, ключей, TLS, локальных данных и неизвестные
ошибки требуют явного вмешательства. Неопределённый результат Discord POST
сначала сверяется с историей и квитанцией, без слепого повторения отправки.

LocalControl сохраняет необязательный recovery в schema=1: идентификатор
ошибки, этап startup/cycle, retry/blocked, сообщение, абсолютный retry_at,
идентификатор ручной операции. Временный сбой не завершает ручную операцию
и не включает автоматику. Сохраняются её номер, ID и срок повтора; перезапуск
их не обнуляет. Интервалы прежние: 60 секунд при подключении, 300 в цикле.
Повторить сейчас использует тот же ID. Отмена доступна только ожидающему
ручному повтору под publisher.lock; повторная проверка ID под блокировкой
и условное сохранение ошибки не позволяют позднему ответу воскресить отмену.
Необязательный cancelled отличает отмену от ошибки в истории интерфейса.

Постоянная ошибка атомарно завершает активную ручную операцию и ставит
автоматику на паузу, сохраняя квитанцию и выбранный номер. Заблокированный
перезапуск не обращается к API до команды пользователя. Повтор после
исправления причины заново читает ключи. Controller и StatusReader используют
одну сохранённую причину и срок. При недоступном файле управления ошибка
сообщается без перезаписи повреждённых данных.

Pipeline.pending отдаёт приоритет единственной начатой публикации текущего
бота в текущем канале. Она не теряется при пустой истории полных глав и может
продолжиться после полуночи. Несколько незавершённых глав, конфликт выбранного
номера или пропавший исходный альбом блокируют продолжение. Полная история
Discord остаётся основанием автоматического выбора; новый счётчик не введён.

В полном пакете теперь 41 файл, в узком — 14; новый failure_policy.py и
изменённые модули источника включены в оба. Добавлены хеши предыдущего
проверенного состояния 8255bca. Отчёт о проверках —
onedelivery_update/RECOVERY_TESTING.md. Старые отчёты сохраняют результаты
своих этапов.

## Версия и диагностика

28.11.2026 пользователь согласовал этап и отдельно уточнил цель будущих
проверок сна/выключения. Работа выполнена в codex/version-diagnostics,
контрольная метка — tested-diagnostics-2026-11-28. Рабочая установка не менялась.

Установщик сохраняет updates/installed_build.json: schema=1, source_commit,
built_at, installed_at, source_dirty и SHA-256 заменяемых файлов. Данные
создаются из манифеста пакета, а не из локального Git установленной программы.
app_version.py проверяет реальные файлы; отсутствующие/повреждённые метаданные
и изменённый код показываются явно. До появления таких метаданных версия
не угадывается по проекту. WorkerStatus также сохраняет идентификатор сборки,
чтобы диагностика могла сравнить обработчик и окно.

Сведения о сборке входят в ту же транзакцию замены/отката. Резервируются
прежние байты; повреждённая копия отвергается до замены кода. Сбой записи новой
версии возвращает прежний код. Повторная установка неизменного пакета сохраняет
дату установки. При успешной замене показываются сборка и путь резервной копии.

diagnostics.py собирает отчёт через явную проекцию полей, без копирования
config, токенов, журналов, URL, имён серверов и полного XML задач. События
производятся из времени запуска, проверок, ошибки и публикации. Текст ошибки
преобразуется в ограниченную категорию, сетевые тела исключений не экспортируются.
Проверка записи использует временный файл в существующей папке и сразу удаляет
его. diagnostic_tasks.ps1 только читает две известные задачи, сверяя действие
с текущей установкой; изменения задач в этом скрипте отсутствуют.

Локальный отчёт открывается фоновым потоком в отдельном окне. Только кнопка
«Проверить связь» читает ключи и выполняет проверку подключения/прав Discord
и первой страницы VK. Pipeline.latest, публикация, загрузка страниц и изменения
команд управления не вызываются. Отчёт сохраняется локально в diagnostics/,
исключённой из Git. Закрытие окна не прерывает публикацию.

## Рабочий процесс

- `main` хранит принятые состояния проекта. Первый коммит — исходная точка
  v7; импорт v9 сохранён следующим коммитом.
- Для каждой доработки создаётся отдельная ветка. Коммит содержит связное
  изменение и описание выполненной проверки.
- Перед коммитом проверяются список файлов и изменения. Не использовать
  массовое добавление без проверки исключений.
- Версии различаются коммитами и тегами, а не новыми папками `v10`, `v11` и т. п.
- Файлы для пользователя передаются через локальную папку проекта;
  не давать веб-ссылки на скачивание.
- Установка отделена от разработки: изменение Git-ветки не должно менять
  запущенную программу, её данные или запускать публикацию в Discord.

## Архитектура настроек

Ручная цель — отдельный объект `expected_override` с идентификатором в
канальном `control.json`. Производное `expected` по-прежнему не является
неоткатываемым счётчиком. Подтверждённая отправка снимает только свою цель;
новая цель не может быть снята старым ответом. Начатая попытка сохраняется
до первого POST и сверяется с полной публикацией при восстановлении.
Изменение цели из окна защищено блокировкой отправки; активная ручная
проверка запрещает смену цели и канала.

Смена назначения использует общий замок настроек, флаг штатной остановки,
блокировки старого/нового канала и publisher.lock. Доступ проверяется через
существующий `runtime.check`, выполняющий только GET. `Pipeline.latest()`
для проверки назначения не вызывается, поскольку восстановление может
редактировать карточку. Конфигурация и задачи резервируются до переключения;
неполный откат запрещает перезапуск обработчика. Секреты и квитанции не переносятся.
Новое назначение всегда остаётся на паузе, его обработчик запускается явно
кнопкой ручной проверки/возобновления либо при последующем входе в Windows.

Списки серверов и каналов используют официальные GET-маршруты
[User Resource](https://github.com/discord/discord-api-docs/blob/main/developers/resources/user.mdx#get-current-user-guilds)
и [Guild Resource](https://github.com/discord/discord-api-docs/blob/main/developers/resources/guild.mdx#get-guild-channels).
Проверка выбранного канала повторяет проверку прав v9 без тестовой публикации.
Разрешены родительские типы 0 (GUILD_TEXT) и 5 (GUILD_ANNOUNCEMENT). Публичные
ветки принимают типы 11 и 10 соответственно; проверка parent_id/guild_id и
полноты страниц сохраняется. Канал объявлений не запускает crosspost автоматически.
[Типы каналов и создание ветки](https://github.com/discord/discord-api-docs/blob/main/developers/resources/channel.mdx#start-thread-from-message).

## Локальное обновление

`onedelivery_update/build_package.py` собирает только изменённые/новые файлы,
фиксирует их SHA-256 и исходный Git-коммит. `payload/` — генерируемый узкий
пакет обновления, исключённый из Git; это не вторая полная версия приложения.
`package.json` также генерируется сборкой. Сборка нормализует окончания строк по .gitattributes: LF для Python/lock,
CRLF для PowerShell/CMD. Установщик принимает известные хеши проверенного
импорта, предыдущего пакета настроек (supported_sources.json) или уже
установленного текущего обновления. Перед остановкой
конкретной задачи захватывает publisher.lock: начатая отправка не прерывается.
Канальная блокировка удерживается вместе с файловой до замены/отката.
Режим задачи восстанавливается, ошибка открытия окна не откатывает установленный код.
При сообщении об ошибке отдельно указывается, завершена ли замена кода.

## Git в среде помощника

Владелец рабочей папки и пользователь изолированной среды могут отличаться.
Если Git сообщает `dubious ownership`, помощник использует параметр
`-c safe.directory=<точный абсолютный путь проекта>` только для текущей команды.
Не применять `safe.directory=*` и не менять глобальные настройки доверия.

Если имя и email автора Git не настроены, используется технический автор `Codex <codex@local.invalid>` через параметры
команды. Личные и глобальные настройки пользователя не меняются.

## Полный пакет

Запрошенный пользователем полный пакет подготовлен в `codex/full-package`
поверх ветки настроек, затем включён в main. Единственная папка актуальных исходников остаётся
`vk_discord_publisher/`; полные копии по версиям не создаются. Сборщик записывает
один `OneDelivery_full.zip` непосредственно из исходников, без промежуточного
полного payload в проекте.

`full_package.py` задаёт явный список 44 рабочих файлов. Конфигурация, DPAPI,
state, downloads, logs, ui и .venv в список не входят. Исторические установщики
stage1/stage2 и старый install.ps1 в полный архив не включаются. Это обновление
полного рабочего кода существующей установки, а не удаление AppData и настройка
заново. Для нового компьютера или утраченной папки данных этот режим не предназначен.

`full_install.refresh` сначала проверяет наличие config.json и двух файлов
токенов, затем использует ту же проверенную транзакцию с явным списком файлов.
Полный откат принимает резервную копию полного пакета; копии старых узких
пакетов на 8/10 файлов не подменяют полный откат. Состав архива проверяется
до извлечения по строгому списку путей, лишние и дублирующиеся записи отклоняются.

Проверки полного пакета: `onedelivery_update/test_full_package.py`.
Отчёт — `onedelivery_update/FULL_TESTING.md`. Старые папки переноса не нужны
полной сборке; удалять их можно после проверки обновлённой программы. Ручное
удаление отслеживаемых Git каталогов не является способом уборки старых версий.
